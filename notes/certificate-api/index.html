Spreading certificate renewals, then fixing the race

AWS Private Certificate Authority · SDE Intern · Sep – Dec 2026

Clients ask the certificate service when a certificate should renew. If every certificate gets the same moment, those renewals arrive together and spike the authority. The API I owned gives each certificate a server-chosen window, so clients come back spread out instead of all at once.

I joined a large Java codebase and had the feature from design through tests within a few weeks. The design covered the data model, what old clients would do, and how the service would behave under load. Two senior-engineer reviews signed off on it.

The lookup had to stay cheap. It is one secondary-index query plus one point read on a distributed NoSQL store, so the cost does not grow with how many certificates exist.

Parallel tests found the bug. Replacing a certificate was a read, a check, then a write. Sixteen concurrent replaces all passed the check, then collided and returned server errors. An atomic transactional write makes exactly one request win. The others fail cleanly instead of erroring.

I also shipped the tests that run a certificate-manager add-on on Kubernetes against the service. Each run creates a temporary cluster, installs the newest add-on releases, and checks an in-place upgrade. Cleanup deletes only the clusters from that run. An in-memory control-plane fake covers the same create, retry, and delete logic in unit tests, with no cloud account.
